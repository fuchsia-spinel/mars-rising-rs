# Mars Rising Rust port — project state

(Rewritten after the ship/weapons milestone; the earlier PROJECT_STATE-1.md was not available in the session, so this is rebuilt from README.md and RE_NOTES.md.)

## Ground rules
- The port reads only *extracted* files (PNG/WAV/JSON/raw tables) produced by `tools/mr_extract.py`; it never touches resource forks.
- Original assets (© Ambrosia Software / David Wareing) are never committed or redistributed.
- **Method, always:** disassemble the original executable first and check everything against it before writing Rust. Since this milestone the check is
  mechanical: run the original routine in `tools/re/ppcemu.py` on random states, write the results to `tests/vectors/`, and make the Rust code reproduce them bit for bit.
- f32 semantics: use `f32`, same operation order as the PowerPC code, `as i32` for `fctiwz`.

### 2026-11-03 (later): the first F6 capture (`capture_576.bin`, ticks 517-576 of level 1)

### 2026-11-03 (evening): second capture, `--upload-every-frame` result
`capture_1214.bin` (ticks 1156-1214): again exactly +1 tick / +1 px per picture and nothing wrong inside the pictures. With the experiment flag the user reports "hitching less, but still hitching, one hitch more notable than the other". So the remaining hitching depends on how the pictures reach the screen, and uniform GPU work helps.
On Windows GLFW paces a windowed OpenGL context with `DwmFlush` before each `SwapBuffers` (that is why the trace shows one ~16.4 ms block per two refreshes plus the upload stall), so the compositor, not the program, decides which refresh shows which picture.
Changes: uploading on every refresh is now the default (`--lazy-upload` restores the old behaviour; `Display::repeat` re-sends the converted picture without converting it again); the trace has two new columns, `marker` (1 on the refresh where F6 was pressed) and `repeat_ms` (time of the repeated upload), so that a capture can be matched with the timing of the same seconds.

### 2026-11-03 (night): third trace (with F6 marker), fullscreen test
User: the hitch was caught in the trace (marker at t = 20.41 s, tick 565); **no hitching in fullscreen**. The trace itself: dt 16.67 +- 0.3 ms on both parities, nothing outside 15.5-17.8 ms after start-up, upload / repeat 15.4-16.5 ms on every refresh (the blocking moved entirely into the upload), **swap 0.07 ms on every refresh** (it does not wait for anything in a window). So in windowed mode the program is paced by the GPU queue's throttling, not by the compositor's refresh, and the phase between its frames and the compositor's refresh drifts (the measured display rate wanders 59.98-60.02 Hz); fullscreen's swap does wait for the refresh.
Change: after the swap, in a window on Windows, `compositor_sync()` calls `DwmFlush` (dwmapi) so that every frame starts just after a compositor refresh; `--no-dwm-sync` turns it off, and it switches itself off if the frames take longer than 22.5 ms on average over 120 frames (the swap would then have waited as well and the frame rate would have halved). The trace has a new column `dwm_ms`. Not compilable here (Windows only code; syntax checked with the cfg forced on).

### 2026-11-03 (late): result of the compositor sync

## 2026-11-08 (later): HUD indicators, sector message, level-start upgrades
- **Shield / lives indicators did not update (fixed, `game.rs`):** the host (`play.rs::sync_hud`) starts its panel over only when `Env::hud_epoch` changes, but every new `Game` started counting at 0, so the first HUD init of a new game had the same epoch (1) as the previous game's and the panel was *not* started over. The new game's `Store` calls (0x1e950) then copied the old game's already drawn panel (spare-ship icons, shield segments, the dimmed absent player) into the clean-background store, and every later `Restore` brought those baked pixels back: the lives and shield bars could not shrink below what the previous game had drawn, and the player-2 dimming was painted twice. The epoch now carries a per-game serial in its high 16 bits (`HUD_GAME_SERIAL`), so a new game always starts the panel over. Test `hud_follows_the_game` checks it. (Not run: no Rust toolchain in the session that made this change.)
- **"Sector N Cleared" stayed after a level change (fixed, `Game::next_level`):** the level set-up `0xd7b0` sets the message state again at `0xdae0..0xdb08` (3 in a demo, 1 otherwise); `next_level` did not, so state 4 of the level just won stayed until the ship entered (then showing the new sector number). Test: `the_level_ends_with_the_coin_bonus_and_the_next_level_keeps_the_ships`.
- **Upgrades at each new sector: matches the original, not changed.** `0x23de4` (ship start) calls `0x26680` (weapon reset), which for every level start raises the weapon level to the sector number (`0xd7a0`, capped at 16: loop at `0x26758..0x26778`) and the special-weapon count to the sector number (cap 10, `0x2677c..0x2679c`); afterwards (`0x23f38..0x23f84`), when `D.13f0` (levels done) > 0 and the weapon level read *before* the reset is >= the sector number, `0x26c94(ship, 1)` adds one more weapon level (same test for the special count with `0x26af4`). `D.13f0` is set to 0 at game start (`0xc768`) and incremented once per completed level (`0xd5b0`). The port reproduces exactly this (`Ship::init`, `Ship::reset_weapons`, vectors in `tests/ship_golden.rs`).
- **Assets folder is optional (`play`, `viewer`):** without a folder on the command line they use `assets` next to the executable, then `assets` in the current directory (`assets::default_assets_dir`, so `cargo run` from the project still works). `play`: the folder is the first argument unless it starts with `--`; `viewer`: unless it is a number (the level). An explicit folder always wins.
